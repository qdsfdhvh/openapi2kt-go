# Null members in nullable open String enums

A plain String or typeless String enum with nullable intent can contain one JSON null and at least one String member. This applies with validation on or off, like the existing open String enum profile. `{"type":["string","null"],"enum":["ready",null,"done"]}` retains a non-null physical enum classifier with READY/DONE and `Unrecognized`; typed nullable views handle JSON null through the nullable codec. A [typeless plain String/null vocabulary](implicit-string-enum-null.md) supplies implicit nullable intent when no explicit nullable/type intent exists. Null never becomes a String enum object.

## Vocabulary, ownership and presence

The parser keeps the original array/member nodes. Duplicate null, duplicate String and invalid literals retain original `/enum/<index>` diagnostics even when null precedes the String values. An explicit String type with a null-only vocabulary and null under a non-null type remain errors; typeless null-only vocabularies keep their separate JsonNull contract. Format/native/value-class/const annotations do not acquire this admission. Raw 240-member limits include null: 239 String literals plus null fit, 240 plus null do not.

The actual original lexical enum owns its classifier, companions and codec. Root/named aliases, internal references and finite borrowed List/Map values retain nearest explicit nullable overrides, actual retained vocabulary identity and all source work. Missing/repeated/replaced declarations or same-byte null-node substitutions cannot authorize borrowing. Canonical enum serializers/descriptors remain non-null; typed nullable or reified aliases use the existing nullable view. Unknown String values still become `Unrecognized` and round-trip.

JSON null differs from the String literal `"null"`. If the original vocabulary contains `"null"`, it retains that actual String member; an unquoted JSON null is Kotlin null. Non-null defaults match original String members; null defaults and required/optional/Patch retain the existing presence policy. Defaults use their existing DTO field roles. [Referenced String enum scalar/collection own defaults](referenced-string-enum-null-member-defaults.md) separately compose these vocabularies with already admitted direct local `$ref` fields, without inheriting target defaults or widening narrowed views. [Finite direct nested String enum collection field defaults](nested-string-enum-collection-defaults.md) reuse this leaf grammar without granting inner/leaf or referenced/named/root defaults; every original vocabulary is checked even for empty/null trees. Request Patch retains Absent, Null and Value with the actual enclosing enum type.

Object-union String tag pins use only actual String vocabulary tokens; the null member adds no tag spelled `"null"`. Null tag payloads follow the existing Unknown/presence dispatch policy. Hierarchy tags retain their existing non-null typed body/mapping behavior and String vocabulary. This does not enforce exact oneOf/intersection match counts. General multi-branch nullable scalar normalization remains excluded; the existing single scalar-plus-null fold can retain this enum.

[Narrowed component alias factories](narrowed-enum-wrapper-defaults.md) validate the complete original nullable vocabulary, then check each own annotation under the nearest alias intent. Original source/default Pointers, independent ownership, strict membership, open runtime strings and existing budgets remain.

## HTTP and compatibility

Named enum request/response bodies and SSE data retain enum codecs, nullable JSON body/result behavior, unknown String and narrowed-view decode failures. Direct inline operation String enum projection remains `String`/`String?` with its approximation warning. Under the tested Ktor configuration, String responses use the existing raw-text reader: JSON text `null` returns the String `"null"`, and a JSON-quoted string retains its quotes. This extension adds no hidden String response codec.

Already accepted successful inputs keep output and wire behavior. Former explicit nullable null vocabulary/default guards preserve their original inputs and now have positive contracts; malformed/non-null/special-profile guards remain. Removing a redundant null from an already nullable vocabulary leaves the same generated declarations and null view. Owned inline vocabulary/default changes participate in dedup/merge/name-lock fingerprints; named references retain the existing nominal-reference fingerprint boundary. Persisted format versions are unchanged.

Original source depth 48, expansion work 16,384, raw enum 240 and constructor/operation slots 240 remain. This is open enum vocabulary admission, not closed membership validation. Null-only literals have their own JsonNull contract; implicit inference beyond plain typeless String/null vocabularies, general composition/String-constraint and actual platform acceptance remain separate.
