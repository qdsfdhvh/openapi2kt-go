# Target property counts in DTO field defaults

With validation enabled, the [direct consuming DTO field-default profile](false-dto-field-defaults.md) also accepts `minProperties` and `maxProperties` on its actual ordinary named target. The consumer still has no component root default. [Independently annotated targets](false-dto-independent-defaults.md) use their separate actual factory proof. Target aliases retain the same nearest nullable intent and do not acquire an annotation or factory.

The annotation's supplied object keys must satisfy the original target counts. A nullable member with a null value counts as one supplied key; an absent optional false member counts as zero. Counts run before decoding or filling missing fields. A required consuming field validates the annotation before suppressing its initializer. A logically nullable target may independently have a consuming null default, after complete target validation.

The final target serializer keeps its existing wire-count policy. In shared DTOs, a required nullable field without an own default can retain the existing default-null initializer; a literal required key does not change that API policy. Re-encoding an all-null object can emit fewer keys under `encodeDefaults=false` or `explicitNulls=false`, and the actual serializer then rejects output below `minProperties`. An admitted annotation does not override caller JSON settings. HTTP serialization has the same behavior.

The source count interval is checked against the actual retained target serializer. Its identity and immutable count values stay bound through deferred annotation planning; replacing or removing those checks cannot retain permission. Original getter/literal/source proof and the existing source48, work16,384, default16,384 nodes/32 KiB, checked16, JVM240 and enum limits remain.

Validation-off counts still reject. Root factories keep their separate contract; wrapper, nested/container defaults, target/consumer component-default combinations and inline/internal/directional/composed targets gain no count permission. Existing accepted output, naming locks and ownership formats require no migration; eligible inputs previously rejected at the target count keyword now generate a field initializer.

These are bounded JVM cases, without broader platform or maximum-combination claims.
