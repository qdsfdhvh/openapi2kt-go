# Named-owner output batches

Local [configuration](configuration.md) generation supports multiple **disjoint output roots**. All selected specs generate in memory before output planning. Unlocked roots retain [version 2 named ownership](output-ownership.md); opt-in [name-lock state](name-lock.md) uses named version4/direct version3 metadata in the same transaction. Unlocked direct-input version1 commands remain unchanged. Existing version 1 trees require [explicit exact-match metadata-only migration](ownership-migration.md); they are not adopted by default.

## Normal-failure transaction

`internal/output.WriteOwnersBatch` is an internal adapter, not a stable public API. It canonicalizes existing ancestor aliases without creating directories and refuses duplicate/overlapping/case-ambiguous roots (`E_OUTPUT_ROOTS`). Each root has its own complete active-owner inventory and selected generated artifacts. A partial `--spec` update passes only the selected spec's root to the batch; unselected roots are not read, locked or modified by output planning.

For generation, the adapter:

1. Preflights every participating root, including manifests, ownership, content hashes, collisions and recovery stages.
2. Acquires all cooperative root locks in canonical sorted order, nonblocking, and holds them until application or rollback finishes. Failure to acquire a later lock releases earlier locks.
3. Replans every root under the complete lock set, preserving intervening owner updates.
4. Stages every changed root on its own filesystem, with its own journal and backups, before applying any root.
5. Applies roots in sorted order; it keeps earlier roots' backups until all roots succeed.
6. On normal application failure, rolls back all transactions in reverse root order. Existing owned files, manifests, handwritten files, file modes and file modification times are preserved when rollback succeeds. Newly created output parent directories are removed only when safe and empty; recursive cleanup is restricted to newly created transaction stages.

Preparation failure occurs before application. `--check` preflights without creating directories, lock files or stages and reports aggregate differences. Unchanged generation preserves output bytes and file modification times, while still participating in cooperative locking. Acquisition can create previously missing output directories/lock files before a later failure; absence of newly created coordination directories is not a normal-generation failure guarantee. Existing coordination file bytes and modification times remain unchanged.

If rollback itself fails, the adapter still attempts rollback of other roots, retains the affected root's journal/backups, and returns `E_RECOVERY_REQUIRED`. Generation and check refuse roots with unfinished stages. Inspect recovery evidence rather than changing manifest versions or clearing an output root.

## Boundaries

This is **not cross-root or cross-file crash atomicity**. A process/OS failure between applies can leave roots at different versions with retained journals/backups; there is no durable multi-root coordinator or automatic crash recovery. Cooperative locks do not protect against arbitrary noncooperating filesystem mutations.

Full ordinary configuration generation reconciles owners only in roots present in the current inventory. Removing an entire root from configuration does not discover or clean its former output. Empty explicit reconciliation addresses the configured default root only. Root relocation/owner renaming is not automatic migration. Explicit [owner rename](output-owner-rename.md) instead maps every selected current spec to an existing version2/4 owner in the same root, preserves all peers without reconciliation, and requires unchanged Kotlin membership/bytes and lock semantics. It compares exact manifest and all owned lock bytes during preflight and under the complete sorted lock set; its metadata-only journal commits each manifest last and never writes Kotlin. [Runtime package relocation/sharing](runtime-package.md) supports existing Patch/bigint helpers with same-root membership. [Configuration coarse metrics aggregation](cli-metrics.md#configuration-aggregation) measures candidate counts and entered batch phases without changing transactions. Specification acquisition is external; this output batch never fetches inputs or consumes/replays stdin. Direct [file/stdin](local-input.md) generation has its separate single-input boundary. Name-lock state participates in these normal-failure transactions with under-lock expected-byte CAS; explicit [disable/reset](name-lock.md#explicit-disablereset-lifecycle) uses the same batch engine and reports classifier/descriptor/file migration impacts. The separate [explicit root move](output-root-move.md) copies one complete manifest-owned v1–v4 source to a concrete target, with exact raw bytes, file attributes, ownership/state CAS and sorted two-root normal-failure rollback. Config requires every original owner in one declared root; partial/disjoint inventory moves remain unsupported. [Explicit same-root v3→v4 adoption](ownership-migration.md#locked-owner-adoption) instead uses exactly one complete configured locked owner, pre-input root/manifest/Kotlin/raw-lock binding, repeated CAS and metadata-only staging; the two actions cannot be combined.

The top-level config report contains one file entry per distinct participating `(root, relative path)` pair; relative paths may repeat across roots. Per-spec summaries identify the source spec, and absolute output roots are not added to the report.

These do not prove cross-platform runtime behavior, crash recovery or arbitrary filesystem fault coverage.
