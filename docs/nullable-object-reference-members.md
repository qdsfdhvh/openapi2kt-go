# Nullable ordinary DTO references in object unions

Object `oneOf` / `anyOf` members may reference an actual ordinary DTO with nullable intent, including a nullable named alias or an intrinsically nullable ordinary DTO. The original target must retain its real constructor and source declaration. The union borrows the existing object fields using its established variant-constructor policy; it does not replace the source DTO or fabricate a catalog entry.

The nearest explicit member/alias true or false controls null intent. Nullable members contribute to the surrounding union's null view. Named root unions retain their Null singleton; inline unions use Kotlin nullable codecs. An explicit false reference to an intrinsically nullable DTO retains its physical fields and contributes no null alternative. Shared/request presence and Patch use the same derived intent. Ordinary allOf intersections follow the separate [nullable operand contract](nullable-intersections.md).

Source nodes, original aliases, actual unique declarations and full cached reference heights are validated through the existing typed DTO authority. Missing, replaced, ambiguous and scratch declarations cannot supply a member classifier. Member nullability does not hide invalid target keywords, required names, field checks or discarded fields. Multiple nullable sources in `oneOf` retain the overlap warning; generation does not validate exact match counts.

This profile covers actual ordinary constructor-bearing DTO targets. General nullable references to other source roles, arbitrary intersection graphs and exact JSON Schema validation remain separate contracts. Source depth 48, work 16,384, checked edges 16, serialized slots 240 and root branch limits remain unchanged.

Previously rejected nullable ordinary DTO union members now generate their original variants and null view; unrelated accepted APIs and wire behavior remain unchanged. ## Composed and internal constructor sources

The same nullable member policy accepts references to ordinary allOf constructor DTOs and unique internal DTOs, including constructors retained under an ordinary allOf/oneOf/anyOf lexical owner. A direct internal Pointer or a finite named alias may supply the original source. For example, a nullable `Owner/allOf/0/properties/node` can supply a union variant while its canonical DTO and serializer remain `OwnerDto.Node`. A standalone union's new subtype uses the terminal Pointer token when it has no component name; this does not create an alias-owned namespace.

Nearest nullable intent is resolved before an internal union alias caches its type. If a branch refers to a forward alias of a nullable DTO, an exported alias to that inline union retains `?`; an explicit false member or alias keeps the non-null codec. This holds for both oneOf and anyOf. Forward resolution uses the existing bounded catalog traversal without expanding nominal DTO fields.

Physical source eligibility is independent of false narrowing. The original lexical catalog, source node/Pointer, alias edges and one retained constructor declaration must still authorize the variant fields. Borrowed variant copies cannot replace a missing original declaration. Root aliases preserve this lexical authority for ordinary DTO leaves in borrowed List/typed Map paths as well.

Nullable allOf intersections now follow the separate [operand contract](nullable-intersections.md). This union-member role does not admit product-union terminals, hierarchy sources/owners, raw or const-only sources, counted source projections, discarded overrides or ambiguous constructors. The original owner must itself be supported; a direct intrinsically nullable inline allOf union alternative remains excluded. Their separate constraints remain in force. Invalid original fields and unsupported keywords still fail before CLI output changes; false narrowing cannot erase source depth or cached alias work.
