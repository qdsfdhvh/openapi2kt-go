# Independent target and consuming DTO defaults

An ordinary named shared consumer's direct DTO-reference field may own an object default while its actual target independently owns an existing [false-member root default factory](false-object-default-members.md). This extends the [consuming field profile](false-dto-field-defaults.md); the consumer still has no component root annotation, and wrappers or intermediate aliases gain no annotation permission.

For example, target root `default: {"value":null,"label":"root"}` and consuming field `default: {"value":null,"label":"field"}` are separate annotations. `TargetDto.default()` returns the root value; `ConsumerDto().target` returns the field value. Each call produces fresh state through the actual target serializer. A consumer without an annotation still initializes its optional field to null; a target alias acquires neither annotation nor factory. Required consuming fields validate their own annotation and keep no initializer.

Both annotations validate independently against original logical nullable/required/false sources. A bad target annotation fails at the target's original `/default`, even when a field supplies a valid value. A bad field annotation fails at the field's original `/default`, even when the target factory is valid. Existing [target count checks](false-dto-field-counts.md), JSON omission, Data/Plain equality and HTTP serialization policies remain.

Permission requires the actual retained target's validated root factory, canonical initializer and literal source identity, together with the actual consumer field/initializer/type/literal proof. Removing or changing the target factory cannot authorize a consuming default. No temporary target declaration grants permission. Existing source depth48, work16,384, default16,384 nodes/32 KiB, checked16, JVM240 and enum limits remain.

Nested/container defaults, consumer component annotations, annotation-bearing intermediate aliases, inline/internal/directional/composed owners and broader graphs retain their separate contracts. Previously rejected eligible independent annotations now generate both APIs; existing accepted output, naming-lock and ownership formats require no migration.
