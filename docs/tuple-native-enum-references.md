# Native enum references in positional arrays

With validation, an existing positional prefix member or explicit `items` tail may follow finite local named/internal aliases to an already admitted Int/Long/Float/Double/Boolean enum source. The terminal retains its plain type/format/enum/nullable grammar and original vocabulary. Bounds, const, caller native overrides, value classes, composition and positional own annotations keep their separate admission rules. Direct inline enums use the [inline enum contract](tuple-inline-enums.md); validation-off native tuple references remain excluded.

Uniform members reaching the same original terminal and effective nullability produce a typed List using the actual scalar codec and checks. Aliases to the same source can be uniform. Distinct vocabularies remain distinct even when their literals or mapped scalars are equal; native enum versus ordinary scalar, different sources or different nullable views produce `List<JsonElement>`. An explicit admitted tail wins only after every original prefix source validates.

`W_TUPLE_APPROXIMATION` remains mandatory. Position and exact length are not enforced, and a typed List can narrow an unrestricted tail. Native enum membership and floating finiteness retain their existing typed-constructor/decode/request/response/SSE boundaries. A standalone transparent scalar List alias codec does not acquire a new runtime constructor barrier. A mixed raw projection does not enforce discarded positional membership. String enum openness and existing numeric/IEEE approximations retain their contracts.

The original component's independently admitted default factory remains its own. No target or alias default becomes a positional initializer, missing List element or consumer default. Required/Patch annotations, nullable narrowing, default suppression and all existing default roles remain separate. A component's valid own annotation cannot hide a malformed or unsupported prefix source behind a tail.

Planning reuses the shared resolver, original lexical catalog, aliases, native vocabulary and actual scalar export authority. A private source registry retains original document paths, ancestor/schema/member/item identities and terminal bytes, including references discarded by a raw or explicit-tail projection. Captures share a cumulative 16,384 node/edge/catalog-work and 8 MiB terminal-byte budget across the new role; repeated nodes reuse their capture. Existing source depth48, per-array reference work16384, checked depth16, enum240, default and JVM240 limits remain. Source syntax is not expanded or rewritten and no enum classifier is synthesized from a positional slot.

Validation-off refusal controls remain separate from these runtime projects. The complete `http` route includes the consumer.

**Migration:** eligible native enum reference members/tails previously rejected and now generate. Previously accepted APIs, codecs/wire behavior, tuple warning policy and persisted ownership/name-lock formats retain their contracts. This does not close general structured/composed tuples, false, nullable recursive graphs or broader platform acceptance.

Boolean `items` tails use the [Boolean tail contract](tuple-boolean-tails.md) with the same original prefix/source and runtime validation gates.

[Selected reference tuple defaults](tuple-reference-defaults.md) also admit independent outer field/root/alias annotations through these existing validation-on sources, with strict original membership and unchanged runtime/standalone-alias boundaries.
