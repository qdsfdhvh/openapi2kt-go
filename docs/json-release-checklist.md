# JSON first-release acceptance checklist

## Objective and status

Deliver an offline, deterministic **OpenAPI JSON 3.0/3.1 → kotlinx.serialization models + bounded Ktor HTTP/SSE client** generator that preserves old output on failure. External tools provide specifications as local files or stdin; consumer projects explicitly invoke the local CLI and do not need a generator Gradle plugin.

**This is a scoped release candidate checklist, not a report that the complete first release is finished.** The bounded `0.2.0-alpha.1` candidate completed the R01–R08 scope, native/JVM, security, toolchain, package installation, review, and release gates and was published. Evidence binds only to that tag; existing alpha assets do not include all recent capabilities. Later source must be bound to and accepted as a new candidate; it does not automatically expand platform scope or complete broader roadmap items.

The candidate is fixed to the **bounded JSON profile** of existing contracts and accepted as a whole under the boundaries below. The original [complete first-release definition of done](development-plan.md#84-first-complete-release-definition-of-done) remains a later roadmap; completing every reference graph is not an exit condition for this candidate, and it does not replace the `1.0.0` [version policy](versioning.md).

This checklist maintains candidate acceptance and release gates. See [implementation status and remaining work](remaining-work.md) for roadmap gaps, existing implementations, and out-of-scope work.

### Status definitions

- **Existing implementation/test entry point**: source and contract are identifiable; this does not mean a particular candidate has been run.
- **Candidate passed**: successful execution evidence binds the same frozen source, inputs, CLI, consumers, toolchain, and options; caches, failed attempts, and unexecuted items must be explicit.
- **Open**: implementation, evidence, or a scope decision is missing. Fix it or explicitly approve and document it as a candidate limitation; do not remove negative cases, relax checks, or raise resource limits to claim completion.

R01–R08 below are closed only for this candidate and explicitly executed profiles. Its full local `all` gate passed, covering unit, fresh models, HTTP/SSE, and all 83 feature routes at freeze time; use `--list` for current source. Existing Go caches and prepared offline dependencies were used, and Kotlin consumers compiled and ran from fresh output. Relevant source/input/consumer content checks remained unchanged; failed attempts and detailed binding records remain in local acceptance materials. [PR #6 CI](https://github.com/qdsfdhvh/openapi2kt-go/pull/6/checks) separately verified native CLI and package installation on three hosts. Later candidates must recheck release gates. Feature contracts define support boundaries; this checklist does not extend them.

## 3. Explicitly external or unpromised capabilities

- **External specification acquisition**: HTTP downloads, authentication, proxies, redirect/retry/cache, and atomic input-file replacement belong to tools such as curl/CI; add no built-in downloader, URL input, or subprocess wrapper. A producer failure after complete JSON cannot roll back generation; callers should inspect pipeline status and obtain a file successfully first when stronger guarantees are needed.
- **Initial JSON scope**: YAML is a later Loader phase; external file/HTTP `$ref`, full OpenAPI/JSON Schema validation, all 3.1 keywords, and Swagger 2.0 are not in the existing commitment.
- **Consumer integration**: use the local CLI and source-set configuration; a formal Gradle plugin, automatic CLI/Ktor plugin installation, application authentication flows, GUI, and other generated languages are not delivered.
- **No additional fault-tolerance promise**: output guarantees are the contract-defined rollback on normal failures, not cross-root/filesystem crash atomicity or automatic recovery. Configuration does not replay stdin; SSE has no generated automatic reconnect by default. Do not hide these limits under “stream/transaction/SSE support.”
- **Other unsupported HTTP features**: multipart, cookie, callbacks, webhooks, links, and similar features continue to follow existing contracts/diagnostics; do not market the HTTP client subset as a complete client.

Deferral of Android/KMP or broader reference graphs is a candidate scope decision, not an automatic conclusion that they are permanently unnecessary.

### Local gate entry point

With Go matching `go.mod` and cached Gradle/JDK/Kotlin dependencies, run in the repository:

```bash
# GO/GOFMT/GRADLE can select existing tools; tools and dependencies are not fetched automatically.
bash scripts/test.sh --list
bash scripts/test.sh all
```

The [script entry point](../scripts/test.sh) `all` runs unit (format/vet/Go/race/Python) → fresh models → fresh HTTP/SSE → all listed feature routes. Generation/Go use offline settings and Kotlin uses cached dependencies and `--offline`; missing tools or failures cannot be bypassed, and existing heap/caps remain. It does not perform cross-host verification, Android/KMP, package installation, history review, or release authorization.

The [CI workflow](../.github/workflows/ci.yml) provides three-host Go, source installation/generation/check, native packages and isolated installation/file/stdin, and tooling/candidate checks. It also configures separate Ubuntu Kotlin/JVM models, HTTP/SSE, and selected profile compilation/runtime jobs. Kotlin dependencies are fetched in an explicit preparation step; generation and acceptance remain offline. A new workflow configuration and local verification do not prove the corresponding GitHub run passed; historical generation-only CI does not automatically gain Kotlin runtime evidence. See the [release contract](releases.md) for release gates.

## 5. Stop conditions

All R01–R08 items must close before candidate release. An explicitly approved scope adjustment may narrow the profiles/hosts/targets to accept, with corresponding notes/documentation/tests updated; it cannot waive pure generation, old-output protection, real evidence, license/security boundaries, or release authorization. When blocked, retain the last successful source, failure logs, unverified items, and required tool or scope decisions. Do not silently change product guarantees, remove failing inputs, fabricate green results, or automatically start unrelated development.

Maintenance of this checklist updates only product boundaries and verifiable entry points; concrete run results, machine paths, and task logs belong in local acceptance records, not public documentation.
